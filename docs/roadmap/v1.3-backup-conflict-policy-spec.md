# v1.3 Backup Conflict Policy Specification

## Scope

This specification defines restore conflict policy requirements before v1.3 backup rollback hardening can change runtime behavior.

## Conflict Types

| Conflict Type | Detection | Required Behavior |
| --- | --- | --- |
| Same key, same checksum | Existing record and backup record are equivalent. | Report as no-op and do not rewrite the record. |
| Same key, different payload | Existing record and backup record differ. | Report conflict and require explicit policy before mutation. |
| Cross-owner mismatch | Backup row owner scope differs from active restore scope. | Reject before mutation. |
| Unsupported store | Backup includes a store not in runtime inventory. | Reject before mutation. |
| Unsupported schema | Backup schema is not accepted by runtime. | Reject before mutation. |
| Invalid required field | Backup row is missing required store key or owner scope. | Reject before staged restore. |

## Allowed Policies

| Policy | Behavior | Runtime Default |
| --- | --- | --- |
| `skip-conflicts` | Import non-conflicting rows and leave conflicting local records unchanged. | Default |
| `replace-conflicts` | Replace conflicting local rows only after explicit confirmation. | Optional |
| `stage-only` | Produce a dry-run report and do not mutate. | Required for preview |

## Rollback Requirements

- Failed dry-run must not mutate IndexedDB.
- Failed staged restore must leave existing records readable.
- Unsupported schemas and unknown stores must reject before mutation.
- Conflict reports must include store name, record key, conflict type, and policy.
- Restore audit report must preserve restored record counts and skipped conflict counts.

## Non-Goals

- Cloud backup restore.
- Server-side merge.
- Remote conflict resolution.
- Deleting local records as rollback.
