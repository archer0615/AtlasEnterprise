# v1.2 Position Migration Plan

## Scope

This plan defines the minimum migration evidence required before a Position runtime store can be implemented.

## Proposed Store

- Store name: `positions`
- Primary key: `positionId`
- Required owner fields: `ownerId`, `householdId`, `portfolioId`
- Required indexes: `ownerId`, `householdId`, `portfolioId`, `assetId`, `status`, `updatedAt`

## Migration Steps

1. Add `positions` to the IndexedDB persistence inventory.
2. Increment `databaseVersion`.
3. Create the `positions` object store in `onupgradeneeded`.
4. Create all owner and query indexes in the same migration.
5. Preserve all existing stores without destructive clears.
6. Mark migration metadata after successful open.
7. Keep backup schema unchanged until backup payload versioning explicitly includes positions.

## Rollback Boundary

Rollback is code-only until the store ships in a release. After release, rollback must leave existing `positions` data untouched and hide the runtime surface instead of deleting user data.

## Required Tests

- Repository contract: create, update, list by owner, list by portfolio, reject cross-owner access.
- Migration chain: positions store and indexes exist while existing stores remain readable.
- Backup gate: positions are excluded until a backup schema version includes them.
- Restore gate: future backup payloads containing positions are rejected before mutation.
- Owner isolation: every persisted position requires `ownerId`, `householdId`, and `portfolioId`.
- Runtime boundary: no broker API, market API, cloud database, or backend dependency.

## Exit Criteria

Position runtime implementation can start only after this plan is referenced by the selected implementation batch and `npm run validate:release` passes on a clean working tree.
